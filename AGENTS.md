## 1. Задача агента

Разработать первую рабочую версию приложения «Дисциплина» для одной семьи.

Приложение помогает родителям формировать у ребёнка базовую учебную дисциплину:

1. Родитель устно даёт ребёнку задание.
2. Фиксирует задание в приложении.
3. Указывает срок выполнения и время проверки.
4. В назначенное время проверяет фактический результат.
5. Фиксирует: выполнено, частично или не выполнено.
6. История заданий и результатов сохраняется.

Первая версия организует действия родителя. Она не оценивает личность ребёнка и не заменяет педагога или психолога.

## 2. Источники истины

При противоречиях использовать следующий приоритет:

1. Этот `AGENTS.md` — техническая архитектура, среда исполнения, процессы и порядок реализации.
2. [`docs/02-domain-model.md`](docs/02-domain-model.md) — модель данных, права и ограничения.

Отдельных документов по процессам, экранам, рискам и порядку сборки в MVP нет: их роль выполняют разделы этого файла. Нерешённые вопросы помечаются в коде как `TODO(open-question)` и не закрываются фиктивным UI.

HTML-вайрфреймы — только визуальный ориентир, не спецификация API или базы данных.

## 3. Пользователи MVP

- Родитель — пользователь приложения.
- В семье может быть несколько родителей.
- Все активные родители равноправны.
- Все родители видят всех детей семьи.
- Любой родитель может создавать, изменять, отменять и проверять задания.
- Ребёнок может получить вход. Аккаунт ему заводит родитель: логин и пароль, без email.
- Ребёнок видит только свои задания (сегодня и историю) и может отметить «сделал» с комментарием.
- Ребёнок не создаёт, не меняет, не отменяет и не оценивает задания, не видит других детей и родительские экраны.
- Отметка ребёнка — не результат. Результат ставит только родитель.

Системный администратор Raspberry Pi — техническая роль вне предметной модели. Он управляет сервером, VPN, резервными копиями и восстановлением доступа, но не получает дополнительных продуктовых прав внутри семьи.

## 4. Среда исполнения

Система работает на одном физическом сервере:

- Raspberry Pi 4 Model B;
- 8 ГБ RAM;
- ARM64;
- Raspberry Pi OS Lite 64-bit;
- основной накопитель — SSD;
- microSD не используется для рабочей базы данных;
- отдельный USB-диск используется для резервных копий;
- сервер постоянно находится дома и подключён к роутеру;
- одна семья;
- доступ к приложению требуется из любой сети.

Все основные данные и сервисы размещаются на Raspberry Pi.

В рабочем режиме запрещены:

- облачная авторизация;
- облачная база данных;
- внешний backend;
- внешний файловый storage;
- Tailscale и другие VPN-посредники;
- Cloudflare Tunnel и аналогичные туннели;
- внешние push-сервисы;
- email-рассылки;
- Telegram-боты;
- облачные резервные копии;
- внешняя аналитика и телеметрия;

Разрешено использование интернета для установки пакетов, обновления ОС и загрузки новых версий приложения.

Для постоянного удалённого доступа нужен статический белый IP от интернет-провайдера. Если провайдер использует CGNAT, заданная архитектура без внешнего посредника не работает. Не пытаться обходить это открытием случайных портов.

## 6. Архитектура L0

### Участники

- Родитель 1.
- Родитель 2.
- Администратор Raspberry Pi.
- Ребёнок: объект реального процесса и пользователь с узкими правами.
- Система «Дисциплина» на Raspberry Pi.

### Взаимодействие

Домашний доступ:
`Телефон или компьютер → домашняя сеть → HTTPS → приложение на Raspberry Pi`

Удалённый доступ:
`Телефон или компьютер → WireGuard VPN → домашний роутер → Raspberry Pi → HTTPS → приложение`

Администрирование:
`Компьютер администратора → WireGuard или домашняя сеть → SSH → Raspberry Pi`

Прямой публичный доступ к API, HTTPS и SSH запрещён.
На роутере наружу пробрасывается только UDP-порт WireGuard.

## 7. Архитектура L1

### 7.1 Host-уровень Raspberry Pi

На ОС работают:

- WireGuard;
- firewall на основе `nftables`;
- локальный DNS, если он потребуется для стабильного внутреннего имени;
- Docker Engine;
- Docker Compose;
- `systemd`;
- синхронизация времени;
- системный планировщик резервного копирования;
- журналирование;
- контроль состояния SSD и свободного места.

### 7.2 Контейнеры

Использовать минимальный набор контейнеров:

1. `caddy`
   - HTTPS;
   - раздача PWA;
   - reverse proxy для `/api`;
   - внутренний сертификат;
   - публичные порты не открываются.
2. `app`
   - HTTP API;
   - локальная авторизация;
   - предметная логика;
   - работа с заданиями;
   - планировщик напоминаний;
   - внутренние уведомления;
   - аудит;
   - обслуживание frontend API;
   - health-check.

Не создавать микросервисы, брокер сообщений, Kubernetes, Redis и отдельный сервис авторизации. Для одной семьи это бессмысленный технический зоопарк.

### 7.3 Хранение данных

Использовать SQLite:

- файл БД хранится на основном SSD;
- включён режим WAL;
- включены foreign keys;
- все критичные изменения выполняются транзакционно;
- контейнер получает отдельный постоянный volume;
- файл БД нельзя размещать на сетевой файловой системе;
- миграции выполняются до запуска новой версии приложения.

SQLite является частью приложения, а не отдельным сетевым сервисом.

## 10. Авторизация

Авторизация полностью локальная.

Требования:

- пароль хранится только как Argon2id-хеш;
- использовать серверные сессии;
- идентификатор сессии хранить в `Secure`, `HttpOnly`, `SameSite` cookie;
- JWT в `localStorage` не использовать;
- реализовать CSRF-защиту;
- проверять активность аккаунта при каждом запросе;
- проверять принадлежность к семье на backend;
- frontend не считается границей безопасности;
- ограничить количество попыток входа;
- журналировать успешные и неуспешные входы без записи паролей.

Логин родителя — email, логин ребёнка — произвольное имя. Письма приложение не отправляет.

Восстановление пароля выполняется локальной административной командой. Не создавать фиктивную кнопку «Забыли пароль», которая ничего не умеет.

## 11. Первоначальная настройка

Первый запуск выполняется в домашней сети:

1. Администратор устанавливает ОС и приложение.
2. Приложение создаёт базу и применяет миграции.
3. Через одноразовый bootstrap-токен создаётся первый `Account`.
4. Создаются `Family`, `Parent`, первый `Child` и `ParentChildRelation`.
5. Bootstrap-токен становится недействительным.
6. Повторная открытая регистрация запрещается.

Bootstrap-токен:

- генерируется локально;
- имеет ограниченный срок действия;
- используется один раз;
- не записывается в репозиторий или образ контейнера.

## 12. Подключение второго родителя

Поскольку внешней почты нет, процесс состоит из двух частей.

### VPN-доступ

1. Администратор создаёт отдельного WireGuard peer.
2. Конфигурация или QR-код передаётся родителю безопасным способом.
3. Родитель подключается к домашнему VPN.

### Доступ к приложению

1. Первый родитель создаёт `FamilyInvitation`.
2. Приложение показывает одноразовую ссылку или код.
3. Код передаётся второму родителю вручную.
4. Второй родитель открывает приложение через VPN.
5. Создаёт аккаунт или входит в существующий.
6. Принимает приглашение.
7. Создаётся `Parent`.
8. Создаются связи со всеми детьми семьи.
9. Новый родитель получает те же права, что и первый.

Повторное принятие приглашения должно быть идемпотентным.

## 13. HTTPS и внутренний адрес

Приложение должно работать только через HTTPS, включая домашнюю сеть.

Допустимый вариант:

- внутреннее имя: `discipline.home.arpa`;
- локальное разрешение имени выполняется Raspberry Pi или домашним роутером;
- WireGuard-клиенты используют домашний DNS;
- Caddy выпускает сертификат через собственный локальный CA;
- корневой сертификат локального CA устанавливается на устройства родителей.

Не отключать проверку TLS и не использовать постоянные предупреждения браузера как «временное решение».

## 14. Firewall

Разрешить:

- UDP-порт WireGuard из интернета;
- HTTPS из домашней сети и WireGuard;
- SSH только из домашней сети и WireGuard;
- DNS только из домашней сети и WireGuard, если используется локальный DNS.

Запретить:

- публичный доступ к API;
- публичный HTTPS;
- публичный SSH;
- прямой доступ к SQLite;
- административные интерфейсы контейнеров;
- Docker socket из приложения.

## 15. Бизнес-инварианты

Обязательно сохранить требования предметной модели:

- один аккаунт MVP принадлежит одной семье;
- все активные родители семьи равноправны;
- каждый активный родитель связан со всеми детьми семьи;
- ребёнка без заданий и повторов можно удалить; ребёнка с хотя бы одним заданием или повтором удалить нельзя; архива у ребёнка нет;
- `due_at` — срок выполнения ребёнком;
- `check_at` — время проверки родителями;
- `check_at >= due_at`;
- время хранится в UTC;
- отображение выполняется в IANA-часовом поясе семьи;
- задание создаётся сразу активным;
- черновиков в MVP нет;
- просрочка вычисляется, а не хранится;
- отменённые задания не удаляются;
- история критичных действий сохраняется;
- проверка результата и закрытие задания выполняются одной транзакцией;
- исправление результата создаёт новую `AssignmentReview`;
- предыдущая проверка не перезаписывается;
- второй родитель видит изменения и результаты;
- ребёнок видит и отмечает только свои задания; отметка ребёнка не закрывает задание и не заменяет проверку;
- отметить можно только активное задание, один раз; повторная отметка — no-op;
- `Recurrence` порождает обычные `Assignment`; сгенерированное задание живёт по тем же правилам, что и разовое;
- на одну дату одного `Recurrence` существует не больше одного `Assignment`;
- изменение или остановка `Recurrence` не меняет уже созданные задания.

## 16. Защита от повторных действий

Все изменяющие команды должны поддерживать идемпотентность.

Обязательные случаи:

- создание задания;
- принятие приглашения;
- проверка задания;
- исправление результата;
- отмена задания;
- создание уведомления;
- генерация задания из `Recurrence`.

Использовать клиентский `command_id` или `idempotency_key` и серверное ограничение уникальности. Для генерации из `Recurrence` ключ — пара `(recurrence_id, occurrence_date)`.

Двойной клик, повтор HTTP-запроса или перезапуск клиента не должны создавать дубликаты.

## 17. Одновременная работа родителей

Требования:

- использовать optimistic locking для изменяемых заданий;
- добавить поле версии либо проверку `updated_at`;
- конфликт не должен молча перезаписывать изменение другого родителя;
- два одновременных результата не должны создавать две текущие проверки;
- все проверки прав и состояния выполняются внутри серверной транзакции.

## 18. Напоминания

Напоминания хранятся в базе данных.

Запрещено полагаться только на таймер в памяти процесса.

После перезапуска приложение должно:

1. найти просроченные необработанные напоминания;
2. обработать их один раз;
3. создать внутренние уведомления родителям;
4. не создавать дубликаты.

Тот же durable-планировщик генерирует задания из `Recurrence` на текущий день по часовому поясу семьи. После перезапуска он догоняет пропущенный текущий день, но не создаёт задания задним числом за прошедшие дни.

Без внешних сервисов поддерживаются только внутренние уведомления:

- список уведомлений в приложении;
- счётчик непрочитанных;
- обновление через polling или SSE при открытом приложении;
- локальное браузерное уведомление, только если браузер уже разрешил его и технически может показать.

Система не обещает разбудить полностью закрытое приложение на телефоне. Не изображать полноценный push там, где его физически нет.

## 19. PWA и offline-режим

PWA должна:

- устанавливаться на телефон;
- кэшировать оболочку интерфейса;
- показывать понятное состояние отсутствия связи;
- повторно подключаться после восстановления сети.

В MVP запрещено выполнять offline-мутации с последующей скрытой синхронизацией. Создание и изменение заданий требуют связи с сервером.

Это сознательное ограничение: конфликтующая offline-синхронизация сейчас не нужна.

## 20. Резервное копирование

Резервное копирование выполняется на второй USB-диск.

Требования:

- ежедневная согласованная копия SQLite;
- нельзя просто копировать рабочий файл БД во время записи;
- использовать SQLite Backup API, `.backup` или эквивалентный безопасный механизм;
- после создания копии проверять её открытие и целостность;
- шифровать архив;
- хранить журнал успешных и неуспешных копирований;
- хранить минимум 7 ежедневных и 4 еженедельных копии;
- предоставить отдельный сценарий восстановления;
- восстановление должно проверяться интеграционным тестом или регулярной ручной процедурой.

Риск остаётся: постоянно подключённый домашний диск не защищает от пожара, кражи и полного уничтожения оборудования.

## 21. Время

Напоминания зависят от корректного системного времени.

Требования:

- включить системную синхронизацию времени;
- хранить часовой пояс семьи отдельно;
- не хранить только UTC-offset;
- уже сохранённые UTC-моменты не пересчитывать автоматически при смене часового пояса;
- после некорректного системного времени не отправлять пачку сомнительных уведомлений без проверки.

Если сервер должен корректно работать после отключения питания без доступа к интернету, потребуется аппаратный RTC-модуль. Это инфраструктурная зависимость, а не задача прикладного кода.

## 22. Надёжность

После перезагрузки Raspberry Pi автоматически запускаются:

- WireGuard;
- firewall;
- Docker;
- Caddy;
- приложение;
- планировщик;
- резервное копирование.

Приложение должно иметь:

- `/health/live`;
- `/health/ready`;
- корректное завершение процесса;
- применение миграций до перехода в состояние ready;
- ограничение размера логов;
- обработку нехватки места;
- понятные сообщения об ошибках;
- отсутствие бесконечных циклов перезапуска.

## 23. Логи

Логировать:

- запуск и остановку приложения;
- применение миграций;
- входы;
- ошибки авторизации;
- значимые команды;
- ошибки фоновых задач;
- обработку напоминаний;
- резервное копирование;
- восстановление;
- системные ошибки.

Не логировать:

- пароли;
- session cookies;
- полные invitation-токены;
- WireGuard private keys;
- секреты шифрования;
- персональные данные без необходимости.

## 24. Обновление приложения

Обновление должно быть воспроизводимым:

1. Создать резервную копию.
2. Загрузить новые ARM64-образы.
3. Остановить приложение.
4. Применить миграции.
5. Запустить новую версию.
6. Проверить health-check.
7. При ошибке восстановить предыдущую версию и данные по документированной процедуре.

Не использовать автоматическое бесконтрольное обновление контейнеров.

## 25. Структура репозитория

Рекомендуемая структура:

- `apps/api/` — backend;
- `apps/web/` — PWA;
- `deploy/compose/` — Docker Compose;
- `deploy/caddy/` — Caddy;
- `deploy/wireguard/` — шаблоны и инструкции без приватных ключей;
- `deploy/firewall/` — правила firewall;
- `scripts/` — установка, обновление, backup, restore;
- `docs/` — архитектура и эксплуатация;
- `tests/` — интеграционные и end-to-end тесты;
- `.env.example` — перечень переменных без секретов.

Секреты, ключи, реальные адреса и пароли не добавлять в Git.

## 26. Порядок разработки

### Этап 0. Каркас

- структура репозитория;
- backend и frontend;
- Docker Compose;
- SQLite и Alembic;
- Caddy;
- конфигурация окружения;
- health-check;
- тестовый pipeline для ARM64-совместимой сборки.

### Этап 1. Вертикальный срез

Реализовать:
`первичная регистрация → семья → ребёнок → задание → список «Сегодня» → проверка → результат → история`

Критерий: один родитель проходит полный цикл.

### Этап 2. Надёжность

- транзакции;
- idempotency;
- optimistic locking;
- аудит;
- обработка повторных запросов;
- восстановление после перезапуска.

### Этап 3. Второй родитель

- приглашение;
- равные права;
- связи со всеми детьми;
- уведомления об изменениях;
- тесты одновременных действий.

### Этап 4. Напоминания и повторы

- durable scheduler;
- внутренние уведомления;
- дедупликация;
- обработка пропущенных заданий после перезапуска;
- `Recurrence` и ежедневная генерация заданий.

### Этап 5. Raspberry Pi deployment

- WireGuard;
- firewall;
- HTTPS;
- локальный DNS;
- backup и restore;
- systemd;
- эксплуатационная документация.

Не начинать с инфраструктуры, полностью оторванной от рабочего вертикального среза. Но и не считать приложение готовым, пока оно запускается только на ноутбуке разработчика.

## 27. Обязательные тесты

1. `check_at < due_at` отклоняется.
2. Родитель другой семьи не получает данные.
3. Двойное создание задания создаёт одну запись.
4. Два родителя одновременно проверяют задание — текущий результат один.
5. Исправление результата сохраняет прошлую проверку.
6. Изменение времени пересоздаёт будущие напоминания.
7. Отмена задания сохраняет его в истории.
8. Новый родитель получает равные права.
9. Настройки уведомлений одного родителя не меняют настройки другого.
10. Повторный запуск worker не дублирует уведомления.
11. Перезапуск Raspberry Pi не теряет задания и напоминания.
12. Пропущенное во время перезапуска напоминание обрабатывается один раз.
13. Приложение недоступно напрямую из интернета.
14. API и SSH доступны через WireGuard.
15. Резервная копия открывается и проходит проверку целостности.
16. Восстановленная база содержит задания, проверки и аудит.
17. ARM64-образы запускаются на Raspberry Pi 4.
18. PWA показывает offline-состояние и не теряет введённые данные без предупреждения.
19. Повторный запуск генерации из `Recurrence` за один день создаёт одно задание.
20. Изменение `Recurrence` не меняет уже созданные задания.
21. Удаление ребёнка с заданием или повтором отклоняется; ребёнок без них удаляется вместе со связями.
22. Ребёнок не получает задания другого ребёнка и не может вызвать родительские команды.
23. Отметка ребёнка не закрывает задание; повторная отметка не создаёт вторую.

## 28. Не входит в MVP

Не реализовывать:

- баллы;
- награды;
- санкции;
- рейтинги;
- серии;
- вложения;
- фотографии;
- массовые действия;
- несколько семей;
- роли owner/admin внутри приложения;
- выборочные права на отдельных детей;
- расширенную аналитику;
- облачную синхронизацию;
- внешние push-уведомления;
- email и Telegram;
- сложную offline-синхронизацию;
- микросервисы;
- Kubernetes.

Повторяющиеся задания с версии 1.1 входят в MVP (см. `Recurrence`). Вход ребёнка и отметка «сделал» — с версии 1.2.

## 29. Правила работы агента

- Сначала изучить `AGENTS.md` и `docs/02-domain-model.md`.
- Не менять предметную модель без явной причины.
- Не додумывать функции, которых нет в MVP.
- Не маскировать нерешённые вопросы фиктивным UI.
- Не ослаблять серверные проверки ради скорости.
- Не хранить данные только во frontend.
- Не удалять историю критичных действий.
- Каждую миграцию сопровождать обратимой процедурой или чётким объяснением необратимости.
- Каждую существенную функцию сопровождать тестами.
- После каждого этапа запускать тесты и показывать результат.
- Не сообщать, что этап готов, если не проверена работа на ARM64 или эквивалентной среде.
- При обнаружении противоречия остановиться, описать его и предложить варианты.
- Не городить абстракции «на будущее», если они не защищают уже зафиксированное расширение модели.

## 30. Definition of Done MVP

MVP считается готовым, когда:

- два родителя могут безопасно работать с одной семьёй;
- можно создавать, изменять, отменять и проверять задания;
- результаты и их исправления сохраняются;
- история не теряется;
- напоминания переживают перезапуск;
- приложение работает на Raspberry Pi 4;
- доступ дома работает по HTTPS;
- удалённый доступ работает через WireGuard;
- приложение не открыто напрямую в интернет;
- backup создаётся и восстанавливается;
- система автоматически запускается после перезагрузки;
- обязательные интеграционные тесты проходят;
- существует понятная инструкция установки, обновления, резервного копирования и восстановления.
